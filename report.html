go-cty Correctness Proof

Three defects in go-cty, shown to exist in both the v1.19.0 release and current upstream main, and shown to be fixed on the fork's main — in the library, in go-cty's own test suite, and in real OpenTofu built from source. pyvider-cty, the Python port, runs the same cases alongside, at its v0.6.1 release. All three are now filed upstream: #226, #227, #228.

The three findings

Each set reads like a patch: − is what upstream go-cty does, + is what the fork does with the fix applied, and py is pyvider-cty on the same cases.

Method

How the evidence was produced

Seven builds, fetched, not copiedEvery go-cty build is downloaded through proxy.golang.org with its checksum verified — upstream v1.19.0, upstream main, each fork fix alone, and the fork's main, where all three are merged. pyvider-cty is installed from GitHub at its v0.6.1 tag. Branches resolve to the commit GitHub has, so no result can come from an unpushed local edit.

Two harnesses, one independent judgeA Go harness is built against each go-cty version, and a Python harness runs the same cases against pyvider-cty; both only record what they observe. A separate judge, which imports neither library, recomputes the right answers from first principles and grades every build.

Tests that fail firstEach fix's own regression test runs 20 times on unfixed upstream source (must fail every time) and 20 times on the fix branch (must pass every time). go-cty's full suite and go vet run on every branch, including the fork's main.

Real OpenTofu, built twiceOpenTofu v1.12.6 is built from the same source against upstream main and against the fork's main — go-cty is the only difference — then planned 30 times per configuration, alongside a stock install.

Finding · cty/value_ops.go · go-cty upstream issue 226

Value.Equals gives different answers for the same objects and maps

ClaimWhen an object or map holds an unknown member and a member that definitely differs, upstream answers cty.False or an unknown bool depending on Go's randomized map iteration order. The fix lets the definite difference win.

MethodEvery pair of flat operands with 1–4 positions, each position p, q or unknown, for objects, maps, lists and tuples — 29,520 pairs plus 3,276 with a sensitive mark — each compared 200 times. Ground truth substitutes p, q and a fresh r for every unknown, in every combination.

Finding · cty/function/stdlib/collection.go · go-cty upstream issue 227

SetProductFunc overflows its length

ClaimThe result length is the product of the argument lengths, multiplied without an overflow check. At 264 it wraps to exactly zero and returns an empty collection; at 263 it wraps negative and the allocation panics. The fix returns an error, and builds each tuple from one reused buffer.

MethodK lists of N elements, with the correct length computed as an exact big integer. Separately, 20,000 random calls — lists, sets and tuples of mixed types, unknown and refined collections, DynamicVal, nulls, marks — run on every build and compared byte for byte.

Rows 48×2 to 62×2 fit in an int but not in any computer's memory, so every Go build — fixed or not — fails the allocation with a recovered panic; the fix covers only lengths an int cannot hold, so these are unstyled. From 63×2 down, unfixed go-cty either silently returns the wrong length or panics uncontrolled; the fix turns every one into a clean result would have too many elements error. All 25 shapes whose result fits in memory are byte-identical between upstream and the fix, and the 20,000 random calls (Go-only; they replay Go's PCG stream byte for byte) agree on all six Go builds.

pyvider-cty multiplies with Python integers, which cannot overflow, and refuses any product over 1,000,000 elements before building it — a deliberate divergence recorded in its parity tracker. It answers every row no machine can build with a clean error instead of an allocation panic. Its 25 buildable products have the same elements, in the same order, as go-cty's; since Go's %#v rendering has no Python equivalent, the comparison uses a language-neutral digest of the elements.

Finding · cty/unknown_refinement.go · go-cty upstream issue 228

Number refinement accepts an empty range when both bounds are exclusive

ClaimassertConsistentBounds chooses its comparison by whether the two inclusivity flags are equal, instead of whether both are inclusive. So 3 < x < 3 is accepted while the equally empty 3 < x ≤ 3 panics.

MethodLower and upper bounds from {−1, 0, 0.5, 1, 1038+1}, every inclusive/exclusive combination, applied lower-first and upper-first — 200 refinements per build. Whether each range contains a number is decided with exact rational comparison.

Scope

What this does not show

  • Equals — operands are flat, with string members drawn from {p, q, unknown}. Nested containers, other element types and refined unknowns go through the same loops but are not enumerated. The OpenTofu runs cover one real configuration, not Terraform itself.
  • SetProduct — the fix adds no size limit below the range of int. Products that fit in an int but not in memory still fail as before, and are deliberately not run.
  • Refinement bounds — the decoder panic on inconsistent wire payloads is pre-existing upstream behaviour; the fix extends it to one more payload.
  • pyvider-cty is tested at its v0.6.1 release, installed from GitHub, as a library only. It has no OpenTofu column, since OpenTofu evaluates expressions with go-cty, not pyvider-cty. It is not part of the random-call replay or the allocation measurements, which are specific to Go. Its own test suite is not run here.
  • All three fixes are filed upstream as issues, since pull requests are disabled on zclconf/go-cty: #226, #227, #228. Nothing further has been proposed; the maintainer fixes accepted issues directly rather than through PRs.
